1 · Introduction and goals

Requirements as files, gates as pull requests, everything else generated

reqTrail keeps the requests, requirements, specs and acceptance records of several projects as Markdown files in Git. A pull request is the only way to change them, so Git holds the trail and GitHub's reviews are the gates. A small engine checks the files, builds an index and publishes a static explorer. This page describes that engine along the twelve sections of the arc42 template, with diagrams at the levels of the C4 model: both are established and free to use, so we reuse them instead of inventing a structure.

What it must do

  • Trace every requirement from the request to the spec, the code, the test and the release, by ID and pinned version.
  • Stop a wrong file at the pull request, not in a review weeks later.
  • Show where work waits, at which gate and for how long.

Top quality goals

  • Safe by design: a rule is a schema, a class or a check, never only a sentence.
  • Maintainable by one small team: one language, no build step, established libraries.
  • Nothing to run: no server and no database; GitHub and static files only.

Stakeholders

  • Requirements owner: decides at G0 and accepts at G3.
  • Principal Engineer: signs the requirement at G1.
  • Architecture owner, with privacy and security when tagged: approves the spec at G2.
  • Tech lead and developers: build and link code and tests. Requesters: bring the needs.

4 · Solution strategy

Six choices that shape everything else

Files are the truth

One Markdown file per item, in Git. Statuses, matrices, release notes and dashboards are derived and never typed in.

Gates are merges

G1 to G3 are pull request reviews with CODEOWNERS and required checks. G0 is a label on the request issue.

Formats are code

One class per object type loads a file only through the JSON Schema of its format version. Each format change comes with a migration.

One language, no build

JavaScript on Node for every check and tool, run from source. Tests with node --test.

Static views

The explorer reads index.json on GitHub Pages. No server, no database, no login of its own.

Reuse before building

Established libraries and standards first: yaml, Ajv, markdown-it, JUnit XML, ReqIF, arc42. Each spec records what was considered.

5 · Building block view

Seven layers, each with its own work packages

C4 levels 2 and 3. Each block names its files and the work packages that build it; the count under it is the number of requirements and planned tests of those work packages, read from the files.

New code or files we writeGitHub feature we configureUsed as is

Dependencies between work packages

Read from depends_on in each feature file: a row lists the work packages that must be finished before it starts. The number in brackets counts the requirements of the row that depend on requirements of that work package; a need without such a link is a form, page or workflow the work package builds on. A check fails when a requirement depends on a work package its own one does not need, directly or through others.

6 · Runtime view

Three scenarios

A requirement changes

  1. The owner works on a branch such as change_request/recipe_box/feature_recipe_box_01_issue31 and raises version for a substantive change once the requirement has passed G1.
  2. The pull request starts validate, text_check and gate_check. The model rejects a wrong field before anything else runs.
  3. Every pin on the old version becomes suspect, and the explorer lists what depends on it.
  4. The Principal Engineer approves (G1) and merges. build_index writes index.json; Pages publishes the explorer.

Evidence arrives

  1. A code repo pull request says implements: req_recipe_box_0003@2.
  2. Its CI runs the tests and keeps the JUnit XML report; a test names the requirement, for example Describe 'req_recipe_box_0003 ConvertTo-RecipeText'.
  3. The nightly build_index reads the last run per requirement and shows it as evidence.
  4. The tech lead opens the acceptance record; the owner accepts it (G3).

The format changes

  1. The engine releases format 2 with format_1_to_2.js, only as a new major version.
  2. A project pinned to @v1 is untouched.
  3. After switching to @v2, the engine reads format 1 through the migration in memory; the runner rejects any change to an ID, a statement or a version.
  4. migrate writes the files in format 2 as one pull request.

8 · Crosscutting concepts

Rules every block follows

IDs and versions

  • IDs such as req_recipe_box_0003 are never reused or renamed.
  • A reference pins a version, @2; a newer target makes it suspect until confirmed.
  • No file holds a status: the index derives it from Git and GitHub.

Names and branches

  • Lower snake case outside code; inside code, the style of the language.
  • Branches are <phase>/<project>/<topic>, or <phase>/<project>/<feature>_<topic> when the change belongs to a feature, for example concept/req_trail/concept_review and concept/recipe_box/feature_recipe_box_01_issue31.

Formats

  • Every project names its format_version; released formats are frozen by checksum.
  • The schemas are the single source of fields and values; conventions.md explains them.

Security

  • Workflows get the least permissions they need; a private code repo is read with a read-only token.
  • Every runtime dependency is named in a merged spec with the libraries considered.

Privacy

  • The repo may be public: validate warns on mail addresses and internal domains in a diff.
  • A requirement that touches personal data carries a privacy review, decided at G2.

Tests and evidence

  • Each acceptance criterion names its test kind: Unit, Integration, Smoke, Static or Manual.
  • A test names the requirement ID; JUnit XML carries it to the index from any language.

12 · Glossary

Terms

TermMeaning
GateA decision point, G0 to G3, with a named gatekeeper; G1 to G3 are pull request merges.
HatA role at a gate, such as Principal Engineer; roles.yml says who wears it.
Pinned referenceA reference with the version it was made against, such as req_recipe_box_0001@1.
Suspect linkA pinned reference whose target has a newer version; it needs a confirmation.
Format versionThe version of the file format a project follows, in project.yml.
MigrationCode that turns files of one format version into the next, without changing their content.
Indexindex.json, built from the files, Git and the test reports; every view reads it.
ExplorerThe static page on GitHub Pages that shows the index; the tracker on the concept page is its demo.
Work packageA unit of the estimate; each is one feature of the project req_trail.

Generated parts: the summary, the constraints, the counts per building block, the dependencies between work packages and the quality requirements are read from concept_data.js, which npm run concept_data writes from the files in projects/.
