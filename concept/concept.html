The full process

From request to technical specification, and back again when something changes

The order is the point: nothing is designed before it is a requirement, and nothing is built before the spec links to it. Each step leaves one file or one GitHub object, and each has a check that can fail.

The same flow as seven steps

1Request

Anyone opens a request with the Request form, or the requirements owner turns a forum post into one. It states the problem, who is affected, how often and the outcome wanted, not a solution. Six yes or no questions tag it for a privacy or security review.

Lives in: issue from request.yml
Gate: G0 at triage
2Requirement

One testable "shall" sentence per file, with priority, owner and acceptance criteria. A reviews field says whether privacy or security looks at it. ID req_prj_0001.

Lives in: requirements/*.md
Check: schema, unique ID
Gate: G1 when merged
3Mockup

An HTML concept page that shows what the user sees. Made from a concept_page template.

Lives in: mockups/*.html
Check: file exists
Gate: G2 with the spec
4Technical spec

Architecture, interfaces and estimate. Links to the requirements it covers, at a version. A tagged requirement adds a short review section.

Lives in: specs/*.md
Check: every link resolves
Gate: G2 when approved
5Approve

G1 to G3 are pull requests that the gatekeeper approves and merges; G0 is a label on the request issue. A workflow tags the baseline at each G2 merge. The data protection officer joins G2 for a request tagged privacy.

Lives in: pull request, CODEOWNERS, tag
6Build and verify

The work issue and the pull request name the requirement IDs. Test names carry the ID. A check comments the link, and the CI run's test results attach as evidence.

Lives in: code repos
Check: tests reference the ID
Gate: G3 when verified
7Change

A new or changed need is a new issue and a pull request. The version rises, unless the fix is editorial.

Lives in: change_request.yml, PR diff
Check: suspect links
Step 7 returns to step 2. A changed requirement marks every spec and test that was reviewed against the old version as suspect until someone confirms it, and the gates it touches open again.
After the release comes the value review. About six weeks later the owner checks whether the problem from the request is solved, against the baseline and target of the feature. It is a review, not a gate: it blocks nothing, and a miss becomes a new request.

Step 6 in detail: how code points back to the requirement

The index cannot guess which code belongs to which requirement. So each place that already exists in your workflow carries one short line with the ID: the work issue, the pull request and the test file. The lines below are examples in the style of recipe_box.

The ticket structure of the issue template stays. One issue can carry several requirement rows. Each row names the global ID with its version, and the sentence is copied from the requirement file at that version, never retyped. A check flags a row whose version is no longer current.

2. Pull request

Add readable ingredients and column
widths to the PDF

implements: req_recipe_box_0003@2,
req_recipe_box_0005@1
Closes #31

Closes #31 closes the work issue in this repo, as today. implements: is the line the index reads, and it can list several IDs. A change with nothing to link says no_req: refactor (or docs, build), so a check can tell "forgot" from "nothing to link".

3. Test file

Describe 'req_recipe_box_0003 ConvertTo-RecipeText' {
    It 'shows an amount with its unit' {
        ...
    }
}

The ID goes into the name of the test or its group, because every test tool writes that name into its JUnit XML report, and the index reads that report. This example is Pester, the test tool of recipe_box; pytest, Jest and most others write the same report, so the engine works with any language. The ID counts only as a whole token, and evidence comes only from that report.

What the checks do with these lines

  • On each pull request a small workflow in the code repo reads implements:, looks the ID up in the generated index and comments one line per ID: status, version and the statement.
  • It fails only when an ID never existed. It warns when the requirement is Draft or In review, which means building before approval, or Approved without a merged spec, which means building before G2. A withdrawn ID also only warns.
  • On merge the PR number fills the Code cell, and the JUnit report of the next CI run fills the Test cell, in the trace matrix.
  • Test results are evidence. The code repo's CI keeps its JUnit XML report as a run artifact. The index reads it, counts the results per requirement ID, for example req_recipe_box_0003: 4 passed, 0 failed, and keeps the commit and the run ID. At G3 the check takes only a run on the merged commit or a later one. Which name each test tool writes into the report is a short spike (B1).
  • It needs no token once the repo is public. The code repo then reads the published index.json from GitHub Pages over plain HTTPS. While the repo is private, it needs a read-only token.
  • Start soft. Comment only for the pilot, and make the check required once the habit holds.

Why bother

  • The question answers itself. "Is req_recipe_box_0003 built and tested?" is a lookup, not a message to a developer.
  • Changes find their code. When a requirement changes, the tool lists the exact pull requests and tests to re-check.
  • Review gets context. The reviewer sees which promise this pull request keeps, in the requirement's own words.
  • Release notes write themselves. Requirements delivered in 0.5, by ID.
  • The cost is small. One line per pull request and the ID in each test group's name. Without it, the link is a table someone edits by hand, and it drifts.

Nothing moves past a gate on goodwill. The tool checks what it can, and a person decides the rest. Two checklists make the decisions concrete: Ready at G1 and Done at G3. What I would change in the four gates

  • Name each gate as a decision. "Concept made" says a document exists. "Concept approved" says someone judged it. The G0 to G3 names above follow your wording with that one change.
  • Put a rough estimate in G1. G2 comes after the signature, so without it you sign blind. Let G2 send a requirement back to G1 when the concept shows it is too big or not possible.
  • Gates attach to different things. G0, G1 and G3 apply to each requirement. G2 applies to the feature's spec, because one spec covers several requirements.
  • Give G3 two keys: evidence and acceptance. The developer who wrote the code does not accept it. Keep it one gate with two approvals; split it into Verified and Accepted only if the Gates view shows that acceptance waits much longer than testing.
  • Do not add a fifth gate. Reviewing whether the outcome was reached is a value review after release: a review, not a gate (see below).

How the gates are controlled

  • G1 to G3 are pull requests into main; G0 is a label on the request issue. Nobody pushes directly. The gatekeeper's approval is the signature, and git history shows who and when.
  • Owner lists pick the gatekeeper. The requirements owners for G0 and G3, the Principal Engineer for G1, the architecture owners for G2. Nobody approves what they wrote, so every owner needs a Principal Engineer who is someone else, and every tech lead an architecture owner who is someone else. The roles dashboard warns when that is missing. One name per hat is enough to start; a second one covers holidays. In an organisation the lists can be teams once the people are members; outside collaborators are named one by one. For the pilot the lists name people (A4). The script that writes CODEOWNERS from roles.yml gives each path exactly one line, because only the last matching line counts. roles.yml and CODEOWNERS belong to the project lead, with the organisation's admin as second code owner, so a change the project lead writes can still be approved. A change to the project lead's own hat needs the admin; gate_check enforces that, because CODEOWNERS knows paths, not lines.
  • The status comes from the gates. The requirement file holds no status; the index derives it. Draft or In review while the pull request is open, Approved after the G1 merge, Specified after the spec merge, Implemented after a merged code pull request that says implements:, Verified after the acceptance record. Merges up to the commit in gates_after of project.yml passed no gate, so the requirements they brought count as Draft, and requirements in open pull requests show as Draft or In review. gate_check refuses an acceptance record without G2, code, test and evidence. The criteria are code, not goodwill.
  • The code repo checks G2 where it matters. The pull request check from step 6 warns when a pull request implements a requirement that has not passed G2. It warns during the pilot and fails after it.
  • Gates reopen on a real change. A requirement keeps version 1 until it passes G1, because nothing is built against a draft. A new version of a requirement after G1 sends it back to Approved and marks its spec and every pinned dependent suspect. A typo fix is marked editorial: the version stays and nothing reopens.
  • Waiting time is measured. The index and the Gates view show how long each item has waited at its gate. A gate that waits more than five working days turns amber; after ten it turns red, and the project lead is mentioned. Without that number, gates become queues.

Ready, at G1

  • One testable "shall" sentence.
  • Acceptance criteria, each one checkable.
  • An owner and a priority.
  • Each criterion starts with its test kind: Unit, Integration, Smoke, Static or Manual.
  • depends_on targets exist, pinned to a version, no cycle.
  • A rough estimate or feasibility note.
  • reviews answered: tagged, or an empty list with a reason.
  • The requester's intent is confirmed, and the pull request links the answer.
  • The text checks raise no warning, or the pull request answers each one.

gate_check tests the fields. A person judges whether the sentence and the criteria are good.

Done, at G3

  • Code and test linked by ID.
  • Evidence stored in the acceptance record: the passed CI run for the tests named with the ID, or a test record for integration, smoke and manual tests.
  • The owner has checked the acceptance criteria (acceptance).
  • Conditions from the G2 review are verified.
  • Docs updated in German and English, or marked not needed.
  • The merged pull request says implements:, so release notes find it.

The German and English docs line is the convention of recipe_box.

Privacy and security: a key, not a gate

  • The default is no review. Every requirement says so in reviews: [] with a reason, so "no" is a decision.
  • Six questions tag a request at G0: personal data, new permissions, data leaving the PC, secrets, code from outside, changes in bulk. The owner proposes the tags at G0; the Principal Engineer confirms them at G1 and answers for a wrong "no".
  • The code repo checks the diff. Its pull request workflow warns when a change adds a new permission scope or a new dependency and the requirement it implements has no review tag, so a wrong "no" shows up. Outbound web calls are not checked: in tools that talk to online services nearly every change makes one.
  • A tag adds a person to G2: the data protection officer for privacy, a named reviewer for security. They read a short spec section: data flow, minimal permissions, secrets, what is logged, rollback.
  • Before the build, because a finding is cheapest in the design. The answer and its conditions are stored in the spec, and the owner checks the conditions at G3.

Value review after release: G4 as a review

  • Six weeks after a release tag, a workflow opens a value review issue for the owner of each feature in it.
  • The question: is the problem from the request solved? The answer is solved, partly or not, next to the outcome KPI before and after (baseline, target, now).
  • A partial or missed answer opens a new request (G0). Nothing is reopened, because the release is done.
  • It blocks nothing, so it is not a gate. The Releases view shows what is due or overdue.

Roles are hats, not people

  • Requirements owner: G0, writes the requirements, and accepts at G3 by approving the acceptance pull request.
  • Principal Engineer: G1. Judges whether a requirement is clear, buildable and testable, confirms the review tags, and approves feature files and KPI entries. May also wear the architecture owner hat.
  • Project lead (team lead): coordinates and holds no gate: plans the people after G1, owns the process rules, the waiting limits and roles.yml, and is mentioned at red.
  • Architecture owner: G2, in the architecture design review (ADR).
  • Tech lead: writes the spec, reviews code, and confirms the evidence at G3 by opening the acceptance pull request, never for a change they developed.
  • Tester: shows the evidence at G3, never for a change they developed. The tech lead may wear this hat for changes they did not develop.
  • Data protection officer: joins G2 for requests tagged privacy.
  • Security reviewer: named per case for requests tagged security.

Decision: private for now, public or GitHub Team before the gates

  • Today it is private, in an organisation on the Free plan. That is enough for the concept, because nothing is enforced yet. It stays private until A1 and A2 are settled.
  • The gates need what a private repo on Free lacks: required code-owner review, protected branches and rulesets, draft pull requests and Pages. A public repo has them for free. GitHub Team adds them to a private repo and is billed per user.
  • Pages is always public. From a private repo it needs GitHub Team, and the site is still public; only GitHub Enterprise Cloud restricts access. With a private repo the explorer needs another home, and the code repos need a token to read index.json.
  • Public needs two OKs. Specs describe permissions and data flows, so information security must agree. Names, roles and approvals are personal data, possibly sensitive, so the data protection officer must agree (review list A1 and A2).
  • Write access for everyone who works on it. Code owners need it, and branch protection keeps every change behind a pull request with the gatekeeper's approval. The intake identity has the role Triage: it opens issues and sets labels, but cannot write files.
  • Check it in the settings. Branch protection under Settings, Branches shows an upgrade prompt where the plan does not allow it. Whether rulesets work on Free for public repos is not confirmed (B5); branch protection is enough for these gates.
  • Licence once public: MIT for the scripts and CC BY 4.0 for requirements and documents (A6). The licence files come with the switch.

The status list gains one value, Specified, between Approved and Implemented, so G2 has a status of its own. A GitHub approval is not an audit-grade e-signature; that stays out of v1. Small changes that touch no requirement skip the gates by saying no_req: in the pull request, as in step 6.

Which setup

  • One shared repo for a small team that trusts each other and has nothing confidential. Least setup.
  • One repo per project as soon as teams are separate or a project is confidential. Each project lead can only change their own project.
  • The format is the same. Both keep the data in projects/<project>/, so a project can move to its own repo later without changing a file. The board spans repos either way, because a GitHub Project can collect issues from many repos.

Why not just a template

  • A GitHub template is copied once. Later fixes to the tools would never reach the copies.
  • So the template holds only data and settings. The tools stay in the engine, and a project repo moves to a new engine version by changing @v1 to @v2 in one pull request.
  • Private project repos need a read-only token of a GitHub App for the hub's overview index; public ones need none.

From need to test: five levels

Each level answers one question and has one home. The request issue is the need. There is no separate need file: the issue number is its permanent name, and a feature points back to it.

1Request (the need)

Why? A problem someone has, in their words. Many requests can feed one feature, and one request can feed several.

Lives in: issue #37
2Feature

Which solution do we pursue? Holds origin, scope and non-scope, risks, the estimate and the outcome metric. Its hats come from roles.yml.

Lives in: features/feature_recipe_box_03.md
3Requirement

What must the system do? One testable sentence with acceptance criteria, owner and review tags.

Lives in: requirements/req_recipe_box_0011.md
4Work issue

What do we change in the code repo? One issue per coherent change. It cites one or more requirement IDs.

Lives in: code repo, issue and pull request
5Test and evidence

Does it work? A test with the ID in its name, and the CI run that passed.

Lives in: tests/, CI result

Why no need_ files? A second ID scheme and a second file type would have to be kept in step with the issues, for little gain. The many-to-many link is the origin: list in the feature file. If that proves too thin in the pilot, a need file can be added later without changing the rest.

How many requirements go into one work issue?

As many as one change proves together. The unit that is tracked, versioned and tested is the requirement ID, not the issue. So the link between requirements and work issues is many-to-many.

One work issue, several requirements

  • One work issue per coherent change, not per requirement.
  • Requirements share an issue when they belong to one user journey, go into one pull request and are tested together. Splitting them only to get one ticket each makes tiny tickets.
  • One requirement can be split over several issues when its parts are built or reviewed separately. It counts as done when every pull request that names it is merged and its tests pass.
  • A pull request lists its IDs with the version: implements: req_recipe_box_0003@2, req_recipe_box_0005@1. The trace matrix then shows that pull request in both rows.

When to keep a requirement apart

  • It is tagged for a privacy or security review. Its own pull request shows the reviewer only what is theirs.
  • It goes into another repo or another release.
  • A bug that breaks a requirement is its own issue. It says violates: req_recipe_box_0003@2, and a failing test is the evidence. If the requirement itself is wrong, it is a change request instead.
  • A change that touches no requirement needs no requirement issue. The pull request says no_req: refactor.

The link is not typed into the requirement file. The index builds it from the implements: lines of merged pull requests and from the requirement rows of the work issues. A hand-kept work_items list would be a second truth, as with need files.

An issue is a ticket and a feature file is a record. Tickets come and go. The record stays and links every ticket that touched it. The work issue keeps its own numbered requirement table, as the issue template defines it; the rows quote the global requirement ID so nothing is written twice.

How a change request is tracked

  1. Open the Change request form in project_management and name the requirement, for example req_recipe_box_0003, with what should change and why. The ID makes the request show up on that requirement.
  2. Triage decides. If accepted, a pull request edits the requirement file and raises version from 2 to 3. The diff is the change record.
  3. Merging marks every spec, test and code link that was reviewed against version 2 as suspect.
  4. The owners of those items confirm or update them. The code change gets a work issue in the code repo that cites req_recipe_box_0003@3.
  5. The request closes when the pull request merges. The requirement's history lists both numbers.

Can one board follow several repos?

  • Yes. A GitHub Project, owned by a user or an organization, can hold issues and pull requests from several repos. Add project_management and each code repo, and use auto-add rules to keep it filled.
  • Custom fields such as Project, Feature and Requirement ID let you group and filter across repos.
  • Links between repos work by reference: writing yourorg/recipe_box#31 in a request issue links the two.
  • Where it is set up: the board work package. Check the field setup in the pilot.

Community intake

From a forum post to a requirement

Most posts in a support community are questions, and answering them is the right end. A post becomes a requirement only when a person decides it should. Two pieces make that cheap: one action that turns a post into a request, and a short weekly triage that makes the decision.

1Post and answer

A member asks, support answers. Most posts end here.

Lives in: community forum
2Mark it

The requirements owner sees a pattern or a clear gap and replies to the post with the marker #request.

Lives in: forum reply
3Request opens

A flow creates a request issue with the post link, an excerpt and the project. It replies in the thread with the issue link.

Lives in: issue, label triage
4Triage, weekly

The requirements owner decides in about 15 minutes and sets one label: accepted, duplicate, needs_info or declined. The reason goes on the issue. The owner also confirms the privacy and security tags.

Lives in: issue labels
5Close the loop

The outcome goes back to the thread. When the requirement ships, the thread gets the release number.

Lives in: forum thread, index

When does a post become a requirement?

  • It asks for a change in what a tool does. "How do I ...?" is support. A wrong or missing guide is a documentation fix: a work issue, no requirement.
  • It recurs, or one person who decides asks for it.
  • It fits a feature we own, a tool in one of our code repos.
  • It is not already a requirement. Search the index first. If it is, add the post link to that requirement: demand goes up by one.

Demand is countable. Posts linked to a requirement show how many people asked. After release, the outcome KPI "support questions per month" shows whether the feature worked.

What the request issue holds

Project:        recipe_box
Source:         link to the community post
Problem:        short excerpt, no names or internal data
Who is hit:     which team, how many posts or people
How often:      for example 12 reports in 90 days

The form asks for the problem and the outcome first. The solution idea is optional, so the owner can still pick a better one. The same rule as for every issue: no secrets, internal names or customer data. The post link stays, and the people who may open it already have access to the community. Once the repo is public, the issue is public too, so no excerpt names a person, a customer or an internal system.

Requests that arrive on GitHub, and votes

Once the repo is public, anyone with a GitHub account can open an issue. That is fine if wishes have one home. The Request form in project_management is that home. A work issue in a code repo is the work package that follows an accepted requirement.

A public issue is a request, not a commitment

  • One inbox for wishes. Code repos keep work issues and bug reports. In each code repo, .github/ISSUE_TEMPLATE/config.yml sets blank_issues_enabled: false and adds a contact link "Request a feature" that points to the Request form. People with write access still see the blank option.
  • Misfiled wishes move. An owner transfers the issue to project_management (GitHub moves an issue between repos with the same owner) or closes it with a pointer.
  • The form says it. A request is not a promise. Gate G0 decides, and the reason is written on the issue for everyone to read.
  • The origin is a label. source_github or source_community. Both follow the same G0.
  • Noise. Required form fields keep out empty requests. Owners can close, lock or block, and GitHub offers temporary interaction limits (check the repo settings). Volume should stay low, because staff reach the repo through the forum, not GitHub.

Voting on GitHub

  • Issues have reactions, not votes. A thumbs-up on the first post works as a vote, and the issue list can be sorted by it. One account gives one thumbs-up. Check the exact sort syntax in GitHub's search help.
  • Discussions have upvotes. People upvote discussions and comments, sort by Top, and start a Poll in its own category. A discussion can become an issue. Turn Discussions on only if public wishes grow.
  • Demand in the index is the thumbs-ups on the request issue plus the number of linked community posts. Staff without GitHub accounts react in the forum. The automation could copy that count; the spike must test it.
  • Votes inform, owners decide. Anyone can open an account and vote, so G0 ranks the requests and the count is one input.

    Formats are code, not prose
    
    
    
      
    How a file becomes an object
      
        
    • One class per object type: project, feature, requirement, spec, acceptance record and metrics.
      • 
        
    • The schema decides. The class loads a file only through the JSON Schema of its project's format_version. A wrong value, a missing field or an unknown key, such as status, never becomes an object, and the error names the file, the field and the rule.
      • 
        
    • One source for fields and values. The templates must match the schemas, and a test compares the tables in conventions.md with them (req_req_trail_0009), so nothing can drift.
      • 
        
    • Objects cannot change after loading, and no class has a status: the index derives it.
      • 
      
    
      
    How a format changes
      
        
    • A released format is frozen. A test compares its schemas with the checksums recorded at the release.
      • 
        
    • Every change is a new format version with a migration from the one before, such as format_1_to_2.js. Without a change, there is no new version and no migration.
      • 
        
    • The runner checks every migration: IDs, statements and versions stay as they are, and the result must pass the new schema.
      • 
        
    • Older formats stay readable. The engine migrates in memory; migrate writes the files as one pull request. A new format comes only with a new major engine version.
      • 
      
    Format 1 is released with engine 1.0. Until then it may still change, because no project outside this repo uses it.
    
    
    
  
    

  
  
    
    
    Quality and editing
    
    
    Better requirement text, and editing without leaving the page
    
    
    Commercial requirements tools check the wording of a requirement and let people edit it in a browser. Both fit this design without a server: the checks run in the pull request, and the explorer hands editing over to GitHub.
    
    
    
      
    Quality checks on the requirement text
      
        
    • Rule-based, warn only. On every pull request, text_check flags vague words ("fast", "user-friendly", "etc.", "as appropriate"), a statement without "shall", two behaviours joined in one sentence, a statement longer than the limit, and acceptance criteria that cannot be checked ("works well"). The word list lives in one file per repo.
      • 
        
    • Duplicates. The check compares a new statement with the index by word overlap and comments the three most similar requirements, so the author can merge instead of adding.
      • 
        
    • AI review, optional. A workflow asks an AI model to review the changed requirements against the same rules and comments its suggestions. It never blocks and never edits. It needs an API key as a secret, and the requirement text leaves GitHub, so the data protection officer agrees first (A2, B13).
      • 
        
    • People still decide. The Principal Engineer approves at G1; the checks make that review faster, they do not replace it.
      • 
      
    
      
    Edit and Propose change buttons
      
        
    • Edit. Every requirement in the explorer links to GitHub's web editor for its file, for example github.com/yourorg/<repo>/edit/main/projects/recipe_box/requirements/req_recipe_box_0003.md. Because main is protected, GitHub offers only a new branch and a pull request; people without write access get a fork. No server and no token in the page (B12).
      • 
        
    • Propose change. For people who would rather not touch YAML, it opens the change request form, filled in with the ID and the version. A workflow turns the form into a pull request that changes the file, so the validator and the gates run as usual.
      • 
        
    • The pull request is the record either way: who changed what, who approved it, and whether the version rose.
      • 
        
    • Both need a GitHub account. Editing inside the page with GitHub sign-in is left out: the sign-in needs a server to keep its secret, and the page would hold a token (D7).

    Status, last change, author, approvalsStatus and history attributesNo file stores them; the export takes them from the index and from git.
    
      
    
    
    
      
    In version 1: the fields and their checks
      
        
    • Every requirement says what kind it is. type is functional, non_functional or constraint; a non-functional requirement also names its category.
      • 
        
    • Every requirement says why. rationale holds one sentence. Notes below the front matter stay optional and are not exported.
      • 
        
    • Value lists are fixed in conventions.md, so a mapping to another tool's values is written once.
      • 
        
    • The statement is plain text: code in backticks is allowed, tables, images, lists and links are not.
      • 
        
    • The validator checks all of it on every pull request, like the other fields (work package 3).
      • 
      
    
      
    Later: export and import
      
        
    • An exporter reads index.json and writes ReqIF first, and CSV for Excel as the cheap option. It needs no new field.
      • 
        
    • Import opens a pull request. A script turns an RM tool's export into requirement files on a branch, so imported requirements pass the gates like any other.
      • 
        
    • One master per project, no two-way sync. Two masters drift apart, and then nobody knows which one is right.
      • 
        
    • Not verified yet: how a given tool maps ReqIF attributes, and whether it keeps the foreign ID on import (B14).

    Assumptions
      
        
    • JavaScript on Node for the tools, the language the explorer needs anyway: plain JavaScript with no compile step and no bundler, the libraries yaml, Ajv and markdown-it, and tests with Node's built-in test runner. The engine's maintainers run them after v1 (C10).
      • 
        
    • One pilot project (recipe_box) with about 12 requirements and 4 specs across two tools.
      • 
        
    • The explorer reuses this page's styles and the concept_page template for mockups.
      • 
        
    • Permissions are GitHub's. project_management is private for now, in an organisation. Everyone who works on it has write access, and branch protection keeps every change behind a pull request with the gatekeeper's approval.
      • 
      
    
      
    Delivery risks
      
        
    • Adoption. If requirements are not written before building, the repo stays empty. The pilot checks this first.
      • 
        
    • A public repo shows everything. Once the repo is public, requirements, KPIs and triage decisions are visible to anyone. Nothing internal goes in, and the intake keeps only the post link and a short excerpt without names.
      • 
        
    • Cross-repo links. A code repo needs one small workflow and a PR template each. Once the repo is public, the workflow reads the index without a token.
      • 
        
    • Forum trigger. The group-message trigger polls, fires on replies too and may not work in every community. The spike tests it before anyone relies on it.
      • 
        
    • Over-writing. Long requirements are hard to review. The schema rejects a statement over 80 words, and text_check warns above 40.
      • 
        
    • Test evidence. Which test name each test tool writes into its JUnit XML report is not verified. A short spike checks it before work package 11 (B1).
      • 
      
    
    
    
    
    Explicitly not in v1
      
      
    • Editing inside the browser page or in Obsidian. The explorer's Edit and Propose change buttons hand over to GitHub's editor and forms; Obsidian is a reader.
      • 
      
    • A generated Obsidian vault and a Quartz site for reading it in a browser, and vote counts in the index. Opening the repo folder in Obsidian works without any of it.
      • 
      
    • An exporter to ReqIF or CSV, an importer, and any two-way sync with an RM tool or Jira. The fields are ready for them (see RM tools).
      • 
      
    • E-signatures and audit reports for regulated approval.
      • 
      
    • Coverage numbers, load tests, environments, deployments, feature flags and monitoring. The tools run on user PCs, so a release is a tag and a ZIP. v1 reads pass or fail per requirement, nothing more.
      • 
      
    • KPI trends over time. They need status history from git and come after the pilot.

    Decisions to make before you build (9)
    
    
    Each has a suggestion.
    
    
      
      
    • A1Review round
      The gates need what a private repo on GitHub Free lacks: enforced code owners, required reviews, protected branches, draft pull requests and Pages for the explorer. A public repo has all of it for free; a paid plan adds it to private repos and is billed per user.
      Suggestion: Stay private while the concept is reviewed and A2 is answered. Then decide: public with strict content rules, or a paid plan. Check the current prices, and whether outside collaborators count as paid seats.
      • 
      
    • A2Review round
      A public repo shows everything, with the whole git history, and nothing can be taken back once it is cloned. Names, roles, reviews and approvals are personal data, and in some organisations membership itself is sensitive. Find out which law applies, whether a deletion request could still be honoured, and how people learn what is published about them.
      Suggestion: A rule «no personal data in the repo»: made-up names and data in requirements, mockups and issues; people appear only as GitHub user names, with their consent; the role history stays private or shows hats without names; everyone commits with GitHub's noreply address. Have your data protection officer check it. This is not legal advice.
      • 
      
    • A3Review roundAuthor
      Requirements owner, Principal Engineer, project lead, architecture owner, tech lead, tester, data protection officer, and a security reviewer named per case. Whoever approves needs write access. Nobody approves what they wrote, so the Principal Engineer must not be the only owner, and the architecture owner not the only tech lead. G3 needs three different people per change: whoever develops it, the tech lead who opens the acceptance pull request, and the owner who approves it.
      Suggestion: Name at least three people. For a two-person pilot, let the owner accept a change they built as long as the tech lead did not build it, and let the index show that as an exception.
      req_trail: One maintainer until work package 5 turns on the required reviews, so the project runs in solo mode and the index marks every solo merge (req_req_trail_0165). Then a second reviewer approves G1 and G2, and G3 follows the two-person rule above.
      • 
      
    • A4Author
      Teams need organisation members; outside collaborators can only be named one by one. roles.yml stays the single source either way.
      Suggestion: Named people for the pilot, teams once the circle grows.
      • 
      
    • A5Review round
      The page says amber after five and red after ten working days, and a value review six weeks after a release. All of it is a guess, and each number lives in one file.
      Suggestion: Start with these numbers and change them after the pilot. At red the project lead is mentioned; nothing else happens by itself.
      • 
      
    • A6Author
      Without a licence nobody may legally reuse the content, although everyone can read it. Scripts and documents can carry different licences.
      Suggestion: MIT for the scripts and CC BY 4.0 for requirements and documents, or one licence for everything. This is not legal advice.
      • 
      
    • A7Review round
      Each requirement row in a work issue names the ID with its version. Copying the sentence makes the issue readable on its own; leaving it out means nothing can drift apart.
      Suggestion: Copy it, with the version, and let a check flag a row whose version is no longer current.
      • 
      
    • A8Author
      Once it is on, GitHub removes every member and outside collaborator who has not set it up.
      Suggestion: Ask everyone first, then switch it on in the organisation's authentication settings.
      • 
      
    • A9Author
      One shared repo keeps approved content safe, because CODEOWNERS gives every project folder its own gatekeepers. But GitHub gives permissions per repo: everyone with write access sees every project, can relabel any issue and push branches anywhere, and all projects share settings and secrets. One repo per project, created from the project template, gives each project its own permissions, branch protection and visibility.
      Suggestion: One shared repo for a small team that trusts each other and has nothing confidential; one repo per project as soon as teams are separate or a project is confidential. The format is the same, so a project can move later (C13).

    Taken into the concept (16)
    
    
    The main design decisions, with the reason.
    
    
      
      
    • C1Review round
      Every gate has a named hat. One person can wear several hats but never approves their own change: GitHub does not let the author approve their own pull request.
      Note: The roles dashboard shows who wears which hat.
      • 
      
    • C2Review round
      The requirement file holds no status; the index derives it. One pull request carries a requirement from draft to G1, and its merge is the approval. After G1 only a new version touches the file.
      Note: A status cannot be set by hand.
      • 
      
    • C3Review round
      The Principal Engineer judges whether a requirement is clear, buildable and testable, confirms the review tags, and approves feature files, KPI entries and new versions. The project lead plans the people, owns the process rules, the waiting limits and roles.yml, and holds no gate.
      Note: In a small team the Principal Engineer and the architecture owner may be one person, who then holds G1 and G2.
      • 
      
    • C4Review round
      The architecture owner approves the spec in the architecture design review. A requirement tagged privacy or security adds the data protection officer or a security reviewer, and the required check reads the requirement files, not a label.
      Note: The default is no review, and «no» is written down with a reason.
      • 
      
    • C5Review round
      The tech lead opens the acceptance pull request with the evidence stored in it, because a link to a run expires. An owner approves it. gate_check fails when the opener holds no tech lead hat or developed the change, or when the acceptor built it.
      Note: One owner is enough.
      • 
      
    • C6Review round
      Code owners need write access, so everyone who works on the project has it, and branch protection keeps every change behind a pull request. A workflow removes accepted when someone outside the owner hat sets it.
      Note: The intake identity gets the role Triage: it opens issues and sets labels but writes no files.
      • 
      
    • C7Review roundAuthor
      A script writes CODEOWNERS from roles.yml, one line per path, because only the last matching line counts. The project lead and the organisation admin are the code owners of roles.yml; a change to the project lead's hat needs the admin, and gate_check enforces that.
      Note: The roles dashboard reads the history of roles.yml.
      • 
      
    • C8Review round
      Six weeks after a release a workflow opens an issue for the owner: is the problem from the request solved? A miss becomes a new request.
      Note: It blocks nothing.
      • 
      
    • C9Review round
      The index and the Gates view show how long each item has waited at its gate.
      Note: Without that number, gates become queues.
      • 
      
    • C10Author
      The validator, the text checks and the index builder are plain JavaScript on Node, the language the explorer needs anyway. So the checks and the views share one toolchain and one set of libraries (yaml, Ajv, markdown-it), and tests run with Node's built-in test runner. Node is on every GitHub runner, and the engine works for code repos in any language, because it reads test results as JUnit XML. The engine's maintainers run the tools after v1.
      Note: Rejected: PowerShell, which needs a module install on every run and reaches fewer people, and Python, which would add a second language next to the explorer. Also rejected: js-yaml, which loses comments, quotes and line breaks when a file is written back. migrate and the propose_change workflow write files back, and their pull requests must show only what really changed.
      • 
      
    • C11Review round
      If a gate has to be bypassed, the admin merges with the label gate_exception, and the index shows it as an exception.
      Note: Better: a second name per gate hat.
      • 
      
    • C12Review round
      The index runs on every merge and once a night, and reads merges, test runs, release tags and value reviews from the code repos: a public repo without a token, a private one with a read-only token.
      Note: Reading run artifacts of another repo is not tried (B7).
      • 
      
    • C13Author
      The tools, schemas, explorer and reusable workflows live in the engine repo req_trail and are released with version tags. A project repo, created from the project template, holds only its data, roles.yml, CODEOWNERS and two-line workflows that call the engine. An optional hub keeps the project names unique, builds an overview index and holds one inbox.
      Note: A GitHub template is copied once, so the tools stay out of it; a project moves to a new engine version with one pull request. Which setup a team uses is A9.
      • 
      
    • C14Author
      Warn-only checks for vague words, a missing "shall", two behaviours in one sentence, length and uncheckable acceptance criteria; similar requirements by word overlap; an optional AI review as a pull request comment. Work package 18.
      Note: The Principal Engineer still decides at G1; the checks make the review faster.
      • 
      
    • C15Author
      Edit opens GitHub's web editor on the file, which creates a branch and a pull request because main is protected. Propose change opens the change request form, filled in; a workflow turns it into a pull request. Work package 19.
      Note: No server and no token in the page; both need a GitHub account.
      • 
      
    • C16Author
      The format is defined in code, not in prose: one class per object type that loads a file only through the schema of its project's format version. A released format is frozen, every change to it is a new version with a migration, and the runner rejects a migration that changes an ID, a statement or a version. Work packages 3 and 17.
      Note: conventions.md explains the format; the schemas define it.
